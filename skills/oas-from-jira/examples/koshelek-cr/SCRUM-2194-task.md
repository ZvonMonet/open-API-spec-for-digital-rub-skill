## Система
КошелёкЦР — модуль, который позволяет банку дать клиентам кошелёк цифрового рубля без переделки ядра банка (АБС).

## Цель
Клиент банка — физическое лицо или индивидуальный предприниматель — открывает счёт цифрового рубля (кошелёк) на платформе Банка России прямо в мобильном приложении банка, не обращаясь в офис.

## Акторы
- Клиент банка — физическое лицо или ИП — инициирует открытие, выбирает тип кошелька, даёт согласия, принимает договор, создаёт ключи.
- Мобильное приложение банка — потребитель API модуля.
- Модуль КошелёкЦР — провайдер API, оркестрирует шаги.
- Госуслуги (ЕСИА) — подтверждают личность и передают данные клиента.
- Платформа цифрового рубля Банка России — проверяет наличие счёта, выдаёт договор, выпускает сертификат, открывает счёт.
- Антифрод — проверяет заявку перед отправкой на платформу.
- АБС — источник данных клиента банка.

## Границы
Входит:
- открытие личного кошелька физического лица (`ownerType = INDIVIDUAL`);
- открытие кошелька ИП для предпринимательской деятельности (`ownerType = SOLE_PROPRIETOR`);
- получение и принятие договора счёта цифрового рубля;
- передача запроса на сертификат ключа проверки ЭП;
- отслеживание статуса заявки и получение данных открытого кошелька.

Не входит:
- пополнение, вывод, переводы, закрытие кошелька;
- рабочее место сотрудника бэк-офиса (просмотр и разбор заявок);
- обработка обратного вызова ЕСИА на сервере банка (служебный endpoint, не часть клиентского API).

## Предусловия
- Клиент аутентифицирован в мобильном приложении (BR-GEN-01).
- Клиент идентифицирован в банке и не заблокирован (BR-GEN-03, BR-GEN-04).
- Клиент — совершеннолетний гражданин РФ (BR-DR-OPEN-01).
- Для кошелька ИП: клиент зарегистрирован в банке как индивидуальный предприниматель (BR-DR-OPEN-15).
- У клиента нет открытого счёта цифрового рубля выбранного типа: физлицо — не более одного личного кошелька, ИП — дополнительно один кошелёк для предпринимательской деятельности (BR-DR-OPEN-04, BR-DR-OPEN-05).
- У клиента нет незавершённой заявки на открытие кошелька того же типа.

## Основной сценарий
[UI] — только интерфейс, [API] — вызов бэкенда модуля, [EXT:<система>] — обращение к внешней системе.

1. [UI] Клиент открывает раздел «Цифровой рубль», нажимает «Открыть кошелёк» и, если он ИП, выбирает тип кошелька: личный или для предпринимательской деятельности.
2. [API] Приложение создаёт заявку на открытие с указанием типа кошелька → [EXT:CORE_BANKING] модуль проверяет предусловия по данным АБС (возраст, гражданство, статус ИП) и наличие кошелька этого типа, открытого через наш банк. Заявка в статусе `CREATED`.
3. [API] Приложение запрашивает ссылку для авторизации в Госуслугах → [EXT:ESIA] модуль формирует запрос авторизации. Заявка — `ESIA_PENDING`.
4. [UI] Клиент авторизуется в Госуслугах и даёт согласие на передачу данных. ЕСИА возвращает результат на сервер банка.
5. [EXT:DR_PLATFORM] Модуль проверяет на платформе, нет ли у клиента счёта цифрового рубля выбранного типа (в т. ч. открытого через другой банк). Заявка — `CONTRACT_PENDING`.
6. [API] Приложение запрашивает договор → [EXT:DR_PLATFORM] модуль возвращает актуальную версию договора счёта цифрового рубля, правила платформы и тарифы.
7. [UI] Клиент изучает условия.
8. [API] Приложение передаёт согласие клиента с указанием версии договора (с ключом идемпотентности). Заявка — `KEYS_PENDING`.
9. [UI] Клиент создаёт ключи ЭП на устройстве; закрытый ключ остаётся на устройстве.
10. [API] Приложение передаёт запрос на сертификат (CSR) → [EXT:ANTIFRAUD] проверка заявки → [EXT:DR_PLATFORM] выпуск сертификата и открытие счёта; для кошелька ИП модуль передаёт на платформу сведения об ИП из АБС. Заявка — `PROCESSING` (асинхронно).
11. [API] Приложение опрашивает статус заявки до `COMPLETED`; в заявке появляется идентификатор кошелька.
12. [UI] Клиент создаёт пароль для доступа к кошельку в приложении. Пароль хранится на устройстве и в API не передаётся.
13. [API] Приложение получает данные кошелька и показывает экран кошелька.

## Альтернативные и исключительные сценарии
- A1. Шаг 2: клиент не проходит по возрасту или гражданству → отказ `CLIENT_NOT_ELIGIBLE`, заявка не создаётся.
- A1a. Шаг 2: запрошен кошелёк ИП, но клиент не зарегистрирован в банке как ИП → отказ `CLIENT_NOT_ELIGIBLE` с причиной «не является ИП».
- A2. Шаг 2: у клиента уже открыт через наш банк кошелёк выбранного типа → отказ `WALLET_ALREADY_EXISTS` с указанием типа. Кошелёк другого типа открытию не мешает.
- A3. Шаг 2: есть незавершённая заявка того же типа → отказ `APPLICATION_IN_PROGRESS`, возвращается её идентификатор.
- A4. Шаг 4: клиент отказал в согласии или учётная запись на Госуслугах не подтверждена → заявка `REJECTED` с причиной `ESIA_CONSENT_DENIED` / `ESIA_ACCOUNT_NOT_CONFIRMED`.
- A5. Шаг 5: платформа сообщает, что счёт выбранного типа уже открыт через другой банк → заявка `REJECTED` с причиной `WALLET_ALREADY_EXISTS`.
- A6. Шаг 7: клиент отказывается от договора → заявка `CANCELLED`.
- A7. Шаг 8: версия договора устарела (Банк России изменил договор) → отказ `CONTRACT_VERSION_OUTDATED`, клиент получает договор заново.
- A8. Шаг 10: антифрод вернул `REVIEW` → заявка `ON_REVIEW`; `DENY` → `REJECTED` с общей причиной, без раскрытия деталей (BR-AF-03).
- A9. Шаг 10: платформа отказала в выпуске сертификата или открытии счёта → `REJECTED`.
- A10. Заявка не завершена в течение 24 часов → `EXPIRED`. 
- E1. Шаги 3, 6, 10: внешняя система недоступна, повторы исчерпаны → ошибка `ESIA_UNAVAILABLE` (шаг 3) / `PLATFORM_UNAVAILABLE` / `UPSTREAM_TIMEOUT`, заявка остаётся в текущем статусе, запрос можно повторить с тем же ключом идемпотентности.
- E2. Шаг 5: платформа недоступна при проверке наличия счёта, повторы исчерпаны → служебный обработчик результата ЕСИА завершается ошибкой 500, заявка остаётся в `ESIA_PENDING`; клиент может заново начать авторизацию (шаг 3).
- E3. Шаг 10: антифрод недоступен, повторы исчерпаны → ошибка `SERVICE_UNAVAILABLE`, заявка остаётся в `KEYS_PENDING`; повтор клиентом снова проходит проверку антифрода.
- E4. Шаги 8 и отмена: клиент не получил ответ (таймаут), а сервер уже выполнил переход → повтор с тем же ключом идемпотентности возвращает итоговый результат, а не ошибку статуса.

## Ключевые данные
- Заявка на открытие: идентификатор, тип кошелька (физлицо / ИП), статус, причина отказа, срок действия, идентификатор кошелька (после открытия), даты создания и изменения.
- Договор: идентификатор, версия, ссылка на документ, ссылки на правила платформы и тарифы.
- Запрос на сертификат: CSR, алгоритм ключа.
- Кошелёк: идентификатор, тип, номер (маскированный), статус, баланс, дата открытия.

## Особенности НФТ
- Синхронные операции модуля — не дольше 2 с (p95).
- Шаг 10 — асинхронный; рекомендуемый интервал опроса статуса — 2 с.
- Вызовы внешних систем повторяются с экспоненциальной задержкой и джиттером (NFR-AV-05); таймаут ЕСИА — 20 с.
- Каждый изменяющий запрос (`POST`) передаётся с ключом идемпотентности (NFR-AV-04).

## Подтверждённые решения
- Для кошелька ИП используются только данные из АБС; дополнительных сведений от клиента не требуется.
- ИП открывает кошелёк для предпринимательской деятельности в том же мобильном приложении.

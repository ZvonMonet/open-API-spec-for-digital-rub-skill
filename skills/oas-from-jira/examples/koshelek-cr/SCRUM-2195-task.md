## Система
КошелёкЦР — модуль, который позволяет банку дать клиентам кошелёк цифрового рубля без переделки ядра банка (АБС).

## Цель
Клиент банка переводит безналичные рубли со своего банковского счёта на свой кошелёк цифрового рубля в мобильном приложении банка и сразу видит результат операции.

## Акторы
- Клиент банка — физическое лицо или ИП — выбирает кошелёк и счёт, вводит сумму, подтверждает операцию.
- Мобильное приложение банка — потребитель API модуля; подписывает распоряжение ключом ЭП клиента на устройстве.
- Модуль КошелёкЦР — провайдер API, оркестрирует операцию.
- АБС — счета клиента, блокировка и списание средств.
- Платформа цифрового рубля Банка России — зачисление на кошелёк, баланс, остаток лимита пополнения.
- Антифрод — проверка операции перед исполнением.

## Границы
Входит:
- пополнение личного кошелька (`INDIVIDUAL`) с текущего рублёвого счёта физического лица;
- пополнение кошелька ИП (`SOLE_PROPRIETOR`) с расчётного рублёвого счёта ИП;
- выбор кошелька-получателя и счёта-источника;
- остаток лимита пополнения (за скользящие 30 дней) для личного кошелька;
- отслеживание статуса операции и баланс кошелька после зачисления.

Не входит:
- вывод средств с кошелька на счёт;
- переводы другим людям, история операций;
- отдельное подтверждение операции кодом (OTP) — достаточно подписи ЭП;
- рабочее место сотрудника бэк-офиса.

## Предусловия
- Клиент аутентифицирован в мобильном приложении (BR-GEN-01).
- У клиента есть кошелёк в статусе `ACTIVE` и действующий сертификат ключа проверки ЭП (business-rules §8.2, §8.7).
- У клиента есть открытый рублёвый счёт в банке, подходящий по типу к кошельку (BR-ACC-01…05).
- Клиент ввёл пароль к кошельку на устройстве; пароль в API не передаётся.

## Основной сценарий
[UI] — только интерфейс, [API] — вызов бэкенда модуля, [EXT:<система>] — обращение к внешней системе.

1. [UI] Клиент открывает свой рублёвый счёт и выбирает «Перевести средства на другой свой счёт».
2. [API] Приложение получает список кошельков клиента для выбора получателя.
3. [UI] Клиент выбирает получателя — кошелёк цифрового рубля.
4. [API] Приложение получает счета клиента, с которых можно пополнить выбранный кошелёк → [EXT:CORE_BANKING] счета и доступные остатки.
5. [API] Для личного кошелька приложение получает остаток лимита пополнения → [EXT:DR_PLATFORM].
6. [UI] Клиент вводит сумму и подтверждает операцию; приложение подписывает распоряжение ключом ЭП на устройстве.
7. [API] Приложение создаёт операцию пополнения (кошелёк, счёт, сумма, подпись) → проверки → [EXT:ANTIFRAUD] оценка → [EXT:CORE_BANKING] блокировка суммы → [EXT:DR_PLATFORM] зачисление. Операция принята к асинхронной обработке.
8. [API] Приложение опрашивает статус операции до `COMPLETED`; после зачисления модуль списывает блокировку в АБС [EXT:CORE_BANKING].
9. [UI] Клиент видит подтверждение и баланс кошелька после операции.

## Альтернативные и исключительные сценарии
- A1. Шаг 7: счёт не принадлежит клиенту, закрыт, не рублёвый или ограничен → отказ `ACCOUNT_NOT_OWNED` / `ACCOUNT_CLOSED` / `ACCOUNT_CURRENCY_NOT_SUPPORTED` / `ACCOUNT_RESTRICTED`, операция не создаётся.
- A2. Шаг 7: тип счёта не подходит к типу кошелька (например, личный счёт для кошелька ИП) → отказ `ACCOUNT_TYPE_NOT_SUPPORTED`.
- A3. Шаг 7: сумма не больше нуля или больше двух знаков после запятой → `VALIDATION_ERROR`.
- A4. Шаг 7: недостаточно средств на счёте → отказ `INSUFFICIENT_FUNDS`.
- A5. Шаг 7: для личного кошелька сумма превышает остаток лимита (300 000 ₽ за скользящие 30 дней) → отказ `TOP_UP_MONTHLY_LIMIT_EXCEEDED` с остатком лимита. Для кошелька ИП лимита нет.
- A6. Шаг 7: кошелёк заблокирован клиентом или ограничен на зачисление → отказ `WALLET_BLOCKED` / `WALLET_RESTRICTED`.
- A6a. Шаг 7: Банк России изменил договор, а клиент ещё не принял новую версию → отказ `CONTRACT_REACCEPTANCE_REQUIRED` (BR-DR-OPEN-09).
- A7. Шаг 7: сертификат клиента недействителен → отказ `CERTIFICATE_INVALID`.
- A8. Шаг 7: антифрод вернул `REVIEW` → операция `ON_REVIEW`; `DENY` → `REJECTED` с кодом `OPERATION_DECLINED_BY_SECURITY`, без деталей (BR-AF-03).
- A9. Шаг 7: платформа отказала в зачислении → блокировка снимается, операция `FAILED` с причиной.
- A10. Шаг 7: повтор запроса с тем же ключом идемпотентности → возвращается та же операция.
- E1. Шаги 4, 5, 7: АБС или платформа недоступны до блокировки суммы → ошибка `CORE_BANKING_UNAVAILABLE` / `PLATFORM_UNAVAILABLE` / `UPSTREAM_TIMEOUT`, операция не создаётся.
- E2. Шаг 7: платформа не ответила после блокировки суммы → операция остаётся в обработке, модуль уточняет статус на платформе; повторная отправка без уточнения запрещена (NFR-AV-03).
- E3. Шаг 7: антифрод недоступен, повторы исчерпаны → ошибка `SERVICE_UNAVAILABLE`, операция не создаётся; повтор клиентом с тем же ключом снова проходит проверку.

## Ключевые данные
- Кошелёк (для выбора): идентификатор, тип, статус, маскированный номер.
- Счёт-источник: идентификатор, маскированный номер, тип, доступный остаток.
- Лимит пополнения: сумма лимита, использовано и остаток за скользящие 30 дней.
- Операция пополнения: идентификатор, кошелёк, счёт, сумма, статус, причина отказа, баланс кошелька после зачисления, даты создания и завершения.

## Бизнес-правила
BR-GEN-01…02, BR-ACC-01…07, BR-AMT-01…04, BR-CNF-01, BR-IDM-01…03, BR-DR-TOP-01…06, BR-DR-OPS-01, 03, BR-AF-01…03, 06, BR-DR-OPEN-09; статусные модели — business-rules §8.2, §8.4, §8.7.

## Особенности НФТ
- Синхронные операции — не дольше 2 с (p95); создание пополнения — асинхронно, интервал опроса статуса — 2 с.
- Не более 1 операции пополнения в минуту на клиента (NFR-RATE-02).
- Вызовы внешних систем повторяются с экспоненциальной задержкой и джиттером (NFR-AV-05).

## Подтверждённые решения
- Лимит пополнения считается за скользящие 30 дней.
- Остаток лимита пополнения учитывает и возвращает платформа цифрового рубля.
- Для подтверждения операции достаточно подписи распоряжения ключом ЭП; отдельный OTP не нужен.

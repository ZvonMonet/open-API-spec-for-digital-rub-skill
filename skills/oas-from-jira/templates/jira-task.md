# Шаблон Task

**Task** описывает фичу целиком: что делает система, кто участвует, основной и альтернативные сценарии, какие системы задействованы. Критерии приёмки живут в связанной **Story** ([[jira-story]]).

## Правила связи

| Правило | Значение |
|---|---|
| Тип связи Task ↔ Story | **relates to** |
| Сколько Story на Task | Одна (ожидаемо). Если связано несколько Story — skill использует все и отмечает это в отчёте. |
| Нет связанной Story | Skill продолжает работу по Task; критерии приёмки выводит из сценариев и помечает как допущения. |
| Тип задачи | `Задача` (Task) |
| Метка | Метка проекта skill (сейчас `ai-skill-sotnikov`) — по ней skill и ментор находят задачи. |

## Поля Jira

| Поле | Что указать |
|---|---|
| Summary | `<Продукт> — <фича>`, например `КошелёкЦР — открытие кошелька цифрового рубля` |
| Description | По шаблону ниже |
| Labels | Метка проекта skill (сейчас `ai-skill-sotnikov`) |
| Linked issues | Story — `relates to` |

## Шаблон Description

Обязательные разделы отмечены `*`. Если обязательного раздела нет, skill не останавливается, а делает допущение и пишет его в отчёт; но каждое такое допущение — повод дополнить задачу.

```markdown
## Система *
<Название продукта или модуля>

## Цель *
<1–3 предложения: какую проблему решает фича и для кого>

## Акторы *
- <Роль> — <что делает в сценарии>
- <Внешняя система> — <роль>

## Границы
Входит:
- <...>
Не входит:
- <...>

## Предусловия *
- <Что должно быть верно до начала сценария; ссылки на BR-ID, если правило есть в knowledge>

## Основной сценарий *
Каждый шаг размечен: [UI] — только интерфейс, [API] — вызов бэкенда модуля, [EXT:<система>] — обращение к внешней системе.
1. [UI] <...>
2. [API] <...> → [EXT:<система>] <...>
3. ...

## Альтернативные и исключительные сценарии
- A1. <Условие> на шаге <N> → <ожидаемое поведение>
- E1. <Сбой> на шаге <N> → <ожидаемое поведение>

## Внешние системы
| Система | Шаги | Синхронно / асинхронно | Контракт |
|---|---|---|---|
| <...> | <...> | <...> | <ссылка на файл в context или документ> |

## Ключевые данные
- <Сущность>: <основные атрибуты>

## Бизнес-правила
- <BR-ID из knowledge/business-rules.md или текст нового правила>

## Особенности НФТ
- <Только то, что отличается от context/non-functional-requirements.md>

## Открытые вопросы
- <...>
```

## Как skill использует разделы

| Раздел | Во что превращается |
|---|---|
| Система, Цель | `info.title`, `info.description` |
| Акторы | Потребитель API, роли в `security` |
| Границы | Что **не** попадает в спецификацию |
| Предусловия | Проверки → ответы 403 / 409 / 422 |
| Основной сценарий: шаги [API] | Операции в `paths` |
| Основной сценарий: шаги [UI] | Не попадают в OAS |
| Основной сценарий: шаги [EXT] | `x-external-systems`, асинхронность (202), ответы 502 / 503 / 504 |
| Альтернативные сценарии | Ответы с бизнес-кодами, статусы |
| Ключевые данные | `components.schemas` |
| Бизнес-правила | `x-business-rules`, проверки |
| Особенности НФТ | `description` операций, 429, заголовки |
| Открытые вопросы | Раздел «Открытые вопросы» отчёта; не додумываются |

## 1. Atlassian Jira

| Термин | Определение | В OAS |
|---|---|---|
| Issue (задача, тикет) | Единица работы в Jira. Имеет ключ, тип, статус, поля. | Источник требований. Трассировка — см. [[oas-conventions#13. Расширения x-*]]. |
| Issue key | Уникальный ключ задачи вида `SCRUM-2194` (ключ проекта + номер). | Трассировка в OAS (`x-jira-key`). |
| Project | Набор задач с общим ключом и настройками. | — |
| Board (доска) | Представление задач проекта (Scrum или Kanban), строится по фильтру. | — |
| Backlog | Список задач, ещё не взятых в спринт. | — |
| Sprint | Ограниченный по времени цикл работы (обычно 1–4 недели). | — |
| Epic | Крупная бизнес-возможность, объединяет истории. Например, «КошелёкЦР». | Обычно соответствует одному API (одному файлу OAS) или группе `tags`. |
| Story (история) | Требование с точки зрения пользователя: «Как <роль>, я хочу <действие>, чтобы <ценность>». | Даёт набор операций (`paths`) для одной фичи. |
| Task (задача) | Техническая или общая работа без пользовательской формулировки. | — |
| Sub-task | Дочерняя задача внутри Story или Task. | Может соответствовать одной операции или интеграции. |
| Bug | Дефект: ожидаемое и фактическое поведение. | Может требовать изменения схем или кодов ответа. |
| Summary | Краткий заголовок задачи. | Основа для `summary` операции. |
| Description | Подробное описание: контекст, сценарии, правила. | Основной источник для `paths`, `schemas`, ошибок. |
| Acceptance Criteria (AC) | Проверяемые условия, при которых задача считается выполненной. Часто в формате Given/When/Then. | Каждый AC → проверяемое поведение: код ответа, поле, ошибка, пример. |
| Status / Workflow | Текущее состояние задачи и допустимые переходы (To Do → In Progress → Done). | — (не путать со статусной моделью бизнес-сущности). |
| Assignee / Reporter | Исполнитель / автор задачи. | — |
| Priority | Важность задачи. | — |
| Labels | Произвольные метки. | Можно использовать для выбора `tags`. |
| Components | Компоненты системы, к которым относится задача. | Подсказка, какой сервис или API затрагивается. |
| Fix Version | Релиз, в который войдёт задача. | Подсказка для `info.version`. |
| Issue links | Связи между задачами: *blocks*, *is blocked by*, *relates to*, *duplicates*, *is part of*. | Связанные задачи — дополнительный контекст (общие сущности, зависимости). |
| Custom field | Поле, добавленное администратором (например, «Критерии приёмки», «Story points»). | Может содержать AC или ссылки на макеты. |
| Comment | Комментарий к задаче. Часто содержит уточнения и решения. | Учитывать как требования, если в них зафиксированы решения. |
| Attachment | Вложение: макет, схема, документ. | Источник полей и сценариев. |
| JQL | Jira Query Language — язык фильтров, например `project = SCRUM AND assignee = currentUser()`. | — |
| Story points | Оценка трудоёмкости в условных единицах. | — |
| Definition of Ready (DoR) | Условия, при которых задачу можно брать в работу. | Чек-лист: достаточно ли в задаче данных для OAS. |
| Definition of Done (DoD) | Условия, при которых задача считается завершённой. | Может включать «OAS согласована и опубликована». |
| Confluence | Вики Atlassian. Часто хранит документацию, глоссарии, схемы интеграций. | Источник контекста, если ссылка есть в задаче. |

## 2. Obsidian

| Термин | Определение | В OAS |
|---|---|---|
| Vault (хранилище) | Папка с Markdown-файлами, которую Obsidian открывает как базу знаний. | Хранилище документов контекста. |
| Note (заметка) | Один `.md` файл. | Один документ контекста (например, описание системы). |
| Frontmatter / Properties | YAML-блок в начале заметки между `---`: метаданные (`type`, `tags`, `status`, `aliases`). | Позволяет отфильтровать нужные документы (например, `type: integration`). |
| Wikilink | Ссылка на заметку `[[Имя заметки]]` или `[[Имя#Заголовок]]`, `[[Имя\|подпись]]`. | Ссылку нужно разрешить в файл и прочитать, если она относится к задаче. |
| Embed | Встраивание содержимого: `![[Заметка]]`, `![[схема.png]]`. | Встроенный контент читается как часть заметки. |
| Alias | Альтернативное имя заметки (`aliases` во frontmatter). | Синонимы терминов, например «АБС» = «Core banking». |
| Tag | Метка `#tag` или в `tags`. | Фильтр документов. |
| Backlinks | Список заметок, которые ссылаются на текущую. | Помогает найти связанный контекст. |
| Callout | Выделенный блок `> [!note]`, `> [!warning]`. | Часто содержит важные правила и ограничения. |
| Template | Шаблон заметки для единообразной структуры. | Шаблоны задач и документов упрощают разбор. |
| MOC (Map of Content) | Заметка-оглавление со ссылками на тематические заметки. | Точка входа в контекст продукта. |
| Canvas | Файл `.canvas` — визуальная доска с карточками и связями (JSON). | Может содержать схемы интеграций. |
| Dataview | Популярный плагин: запросы к заметкам по их свойствам. | — |
| Attachments folder | Папка для вложений (картинки, PDF). | Источник схем и макетов. |

## 3. Банк и банковское приложение

| Термин | Определение | В OAS |
|---|---|---|
| Клиент (физлицо) | Пользователь услуг банка. Идентифицируется внутренним ID клиента. | `clientId` обычно берётся из токена, а не передаётся в теле. |
| ДБО | Дистанционное банковское обслуживание: мобильное приложение, интернет-банк. | Основной потребитель (consumer) API. |
| Мобильное приложение / фронт | Клиентская часть, вызывает API бэкенда (часто через BFF или API Gateway). | Клиент API; определяет, какие данные нужны на экранах. |
| BFF (Backend for Frontend) | Слой API, заточенный под конкретный клиент (мобильный, веб). | OAS может описывать именно BFF-слой. |
| Бэк-офис | Внутренние сотрудники и системы банка: проверка, сопровождение, разбор инцидентов. | Отдельный набор операций, другие роли и `security`. |
| АБС | Автоматизированная банковская система (core banking): счета, остатки, проводки, клиентская база. | Внешняя система (provider) для модуля; данные счёта и клиента. |
| CRM | Система управления взаимоотношениями с клиентами. | Иногда источник контактных данных. |
| Процессинг | Система обработки карточных операций. | — |
| Счёт (текущий) | Банковский счёт клиента. Номер — 20 цифр. | `accountNumber`: `type: string`, `pattern: '^\d{20}$'`. |
| БИК | Банковский идентификационный код, 9 цифр. | `pattern: '^\d{9}$'`. |
| ИНН | Идентификационный номер налогоплательщика; у физлица 12 цифр. | `pattern: '^\d{12}$'`. |
| СНИЛС | Страховой номер индивидуального лицевого счёта, 11 цифр. | ПДн, маскировать в логах. |
| ПДн | Персональные данные. Регулируются 152-ФЗ. | Разметка и маскирование — по [[sensitive-data]]. |
| Согласие | Зафиксированное согласие клиента (на обработку ПДн, условия договора, обмен данными). | Отдельная сущность: id, тип, версия документа, время, канал. |
| KYC / идентификация | Проверка личности клиента. По 115-ФЗ бывает упрощённая и полная. | Бизнес-правило-предусловие; ошибка, если уровень недостаточен. |
| ПОД/ФТ (AML) | Противодействие отмыванию доходов и финансированию терроризма (115-ФЗ). | Возможные отказы и проверки. |
| Антифрод | Система выявления мошеннических операций. Решение: допуск, отказ, дополнительная проверка. | Внешняя система; результат влияет на статус и коды ошибок. |
| Лимит | Ограничение по сумме или количеству операций. | Бизнес-ошибка «превышен лимит». |
| OTP | Одноразовый код подтверждения (SMS, push). | Отдельные операции «отправить код» и «подтвердить код». |
| 2FA / MFA | Двух- или многофакторная аутентификация. | — |
| ЕСИА / Госуслуги | Единая система идентификации и аутентификации; получение подтверждённых данных гражданина. | Внешняя система; согласие на обмен данными. |
| СБП | Система быстрых платежей Банка России, переводы по номеру телефона. | — (аналог по смыслу для переводов по телефону). |
| Операция | Действие клиента, меняющее состояние (перевод, пополнение). | Сущность `Operation` со статусом, суммой, датой. |
| Проводка | Бухгалтерская запись в АБС (дебет/кредит). | — |
| Холдирование (блокировка средств) | Временная блокировка суммы на счёте до завершения операции. | Промежуточный статус операции. |
| Комиссия / тариф | Плата за операцию по тарифам банка. | Поле `fee` в ответе. |
| Выписка / история операций | Список операций за период. | Операция списка с пагинацией и фильтрами. |
| Резидент / нерезидент | Налоговый и валютный статус клиента. | Возможное бизнес-правило. |

## 4. Цифровой рубль

| Термин | Определение | В OAS |
|---|---|---|
| Цифровой рубль | Цифровая форма национальной валюты, эмитируемая Банком России. Регулируется законом о цифровом рубле (161-ФЗ «О национальной платёжной системе» с изменениями 340-ФЗ). | — |
| Платформа цифрового рубля | Информационная система Банка России, где учитываются цифровые рубли и проводятся операции. Оператор — Банк России. | Внешняя система (provider) для модуля КошелёкЦР. |
| Участник платформы | Финансовая организация (банк), подключённая к платформе и обслуживающая клиентов. | Наш банк; интеграция с платформой идёт от его имени. |
| Пользователь платформы | Клиент (физлицо, юрлицо, ИП), имеющий счёт цифрового рубля. | Клиент API. |
| Тип владельца кошелька | Физлицо (личный кошелёк) или ИП (кошелёк для предпринимательской деятельности). Определяет лимит количества кошельков. | `ownerType`: `INDIVIDUAL`, `SOLE_PROPRIETOR`. |
| Счёт цифрового рубля («кошелёк») | Счёт на платформе, открываемый по договору с Банком России. Ведётся не в АБС банка. «Кошелёк» — бытовое название. | Сущность `Wallet`: id на платформе, статус, баланс. |
| Договор счёта цифрового рубля | Договор между пользователем и Банком России; банк-участник выступает посредником. | Сущность документа: id, версия, формат, ссылка; факт акцепта. |
| Пополнение (зачисление) | Перевод безналичных рублей со счёта в банке на счёт цифрового рубля. | Операция: списание в АБС → зачисление на платформе (часто асинхронно). |
| Вывод (обратный обмен) | Перевод цифровых рублей обратно на банковский счёт. | Операция в обратном направлении. |
| Перевод по номеру телефона | Перевод другому пользователю платформы с поиском получателя по телефону. | Операции «найти получателя» и «создать перевод». |
| Электронная подпись (ЭП) | Криптографическая подпись для подтверждения операций и доступа. | Подпись запросов или операций; поле `signature`. |
| Ключ ЭП / ключ проверки ЭП | Закрытый ключ (хранится у владельца, не передаётся) и открытый ключ для проверки подписи. | В API передаётся только открытый ключ или запрос на сертификат. |
| Сертификат ключа проверки ЭП | Документ, связывающий открытый ключ с владельцем. Выпускается удостоверяющим центром. | Сущность `Certificate`: id, серийный номер, срок действия, статус. |
| CSR | Certificate Signing Request — запрос на выпуск сертификата с открытым ключом. | Поле `csr`: строка Base64 или PEM. |
| СКЗИ | Средство криптографической защиты информации (сертифицированное ФСБ). | НФТ: где выполняются криптооперации. |
| ГОСТ Р 34.10-2012 / 34.11-2012 | Российские стандарты подписи и хеш-функции («Стрибог»). | Указывать алгоритм в описании полей подписи и ключа. |
| Офлайн-режим | Возможность операций без связи с платформой (заявленная функциональность). | — для текущих фич. |
| Смарт-контракт | Автоматически исполняемое условие операции на платформе. | — для текущих фич. |

> [!important] Бизнес-правило: количество кошельков на платформе
> - **Физическое лицо** — не более одного счёта цифрового рубля на платформе Банка России, независимо от количества банков.
> - **Индивидуальный предприниматель** — до двух: один как физическое лицо, второй для предпринимательской деятельности.
>
> В OAS:
> - Тип владельца кошелька — поле `ownerType` (`enum: [INDIVIDUAL, SOLE_PROPRIETOR]`).
> - Попытка открыть сверх лимита → `409 Conflict` с бизнес-кодом `WALLET_ALREADY_EXISTS`. В ответе указывается, какой тип кошелька уже открыт.
> - Кошелёк, уже открытый через другой банк, тоже считается: проверка идёт по данным платформы, а не нашей БД.

## 5. OpenAPI Specification

### 5.1 Общие понятия

| Термин | Определение | В OAS |
|---|---|---|
| OpenAPI Specification (OAS) | Стандарт машиночитаемого описания HTTP API в YAML или JSON. Ранее назывался Swagger. | Итоговый артефакт. |
| Версии OAS | 3.0.x — самая широко поддерживаемая инструментами; 3.1.x — полная совместимость с JSON Schema 2020-12, добавлены `webhooks`; 3.2 — последняя линия (2025). | Принятая версия — в [[oas-conventions#1. Версия и файл]]. |
| Swagger 2.0 | Предыдущая версия стандарта (`swagger: "2.0"`). | Не использовать для новых спецификаций. |
| JSON Schema | Язык описания структуры JSON-данных. OAS использует его для схем. | Основа раздела `components.schemas`. |
| YAML | Человекочитаемый формат данных; основной формат OAS-файлов. | Отступы пробелами, без табов. |
| Contract-first (API-first) | Подход: сначала согласуется контракт (OAS), потом пишется код. | Наш случай. |
| Code-first | Спецификация генерируется из кода. | — |

### 5.2 Структура документа

| Элемент | Определение | Пример / правило |
|---|---|---|
| `openapi` | Версия стандарта. | `openapi: 3.0.3` |
| `info` | Метаданные: `title`, `version`, `description`, `contact`. | `version` — версия API, не версия стандарта. |
| `servers` | Базовые URL окружений; поддерживает переменные. | `https://api.bank.example/wallet/v1` |
| `tags` | Группы операций для навигации. | По фичам: `Wallet Opening`, `Top-up`. |
| `paths` | Набор путей (ресурсов) и операций над ними. | `/wallets`, `/wallets/{walletId}` |
| Path item | Объект одного пути; содержит операции по HTTP-методам. | `get`, `post`, `put`, `patch`, `delete` |
| Operation | Одна операция = путь + метод. | Имеет `operationId`, `summary`, `parameters`, `requestBody`, `responses`. |
| `operationId` | Уникальный идентификатор операции; используется генераторами кода. | Правило именования — [[oas-conventions#4. Пути и операции]]. |
| `summary` / `description` | Краткое и подробное описание. `description` поддерживает Markdown. | В `description` — бизнес-правила и ссылка на задачу. |
| `parameters` | Параметры запроса; поле `in`: `path`, `query`, `header`, `cookie`. | Path-параметры всегда `required: true`. |
| `requestBody` | Тело запроса: `content` по media type и `schema`. | `application/json` |
| `responses` | Ответы по HTTP-кодам; `default` — для любых неописанных. | Описывать успешные и ошибочные ответы. |
| Media type | Тип содержимого: `application/json`, `application/problem+json`, `application/pdf`, `multipart/form-data`. | Для ошибок — см. [[oas-conventions#8. Ответы и ошибки]]. |
| `headers` | Заголовки ответа. | `Location`, `Retry-After`, `ETag`. |
| `components` | Переиспользуемые объекты. | `schemas`, `parameters`, `responses`, `requestBodies`, `headers`, `examples`, `securitySchemes`. |
| `$ref` | Ссылка на объект в этом или другом файле. | `$ref: '#/components/schemas/Wallet'` |
| `security` | Требования безопасности: глобально или на операцию. | `security: [{ bearerAuth: [] }]` |
| `securitySchemes` | Описание схем аутентификации: `http` (bearer), `apiKey`, `oauth2`, `openIdConnect`, `mutualTLS` (3.1). | См. [[#8. Безопасность интеграций]]. |
| `callbacks` | Описание запросов, которые наш сервер отправит потребителю после операции. | Для асинхронных уведомлений. |
| `webhooks` (3.1+) | Входящие события, не привязанные к конкретной операции. | Уведомления о смене статуса. |
| `links` | Связь ответа одной операции с параметрами другой. | `walletId` из ответа → `GET /wallets/{walletId}`. |
| `examples` / `example` | Примеры значений. | Реалистичные, без настоящих ПДн. |
| `deprecated` | Пометка устаревшей операции или поля. | `deprecated: true` |
| Extensions (`x-*`) | Пользовательские поля спецификации. | Перечень принятых расширений — [[oas-conventions#13. Расширения x-*]]. |

### 5.3 Ключевые слова схем

| Ключевое слово | Смысл | Правило |
|---|---|---|
| `type` | Тип: `string`, `integer`, `number`, `boolean`, `object`, `array`. | В 3.1 допускается массив типов: `[string, "null"]`. |
| `format` | Уточнение формата: `uuid`, `date`, `date-time`, `email`, `int64`, `byte`, `binary`, `uri`. | Принятые форматы — [[oas-conventions#6. Типы данных]]. |
| `properties` | Поля объекта. | Именование — [[oas-conventions#5. Схемы и поля]]. |
| `required` | Список обязательных полей объекта. | Указывать явно. |
| `nullable` (3.0) | Поле может быть `null`. В 3.1 удалено, вместо него `type: [x, "null"]`. | Зависит от версии OAS. |
| `enum` | Допустимые значения. | Статусы и типы; именование — [[oas-conventions#5. Схемы и поля]]. |
| `pattern` | Регулярное выражение для строки. | Номера счетов, телефоны. |
| `minLength` / `maxLength` | Длина строки. | — |
| `minimum` / `maximum` | Границы числа. | Суммы > 0. |
| `minItems` / `maxItems` | Размер массива. | — |
| `items` | Схема элементов массива. | — |
| `additionalProperties` | Разрешены ли поля сверх описанных. | Часто `false` для строгих контрактов. |
| `readOnly` / `writeOnly` | Только в ответе / только в запросе. | `id`, `createdAt` → `readOnly`; пароль → `writeOnly`. |
| `allOf` | Композиция: объект соответствует всем схемам. | Наследование и расширение. |
| `oneOf` | Ровно одна из схем. | Варианты тела; обычно вместе с `discriminator`. |
| `anyOf` | Одна или несколько схем. | Использовать редко. |
| `discriminator` | Поле, по которому выбирается вариант `oneOf`. | `propertyName: type`. |
| `default` | Значение по умолчанию. | — |
| `title` / `description` | Название и описание схемы или поля. | Описание на языке команды; бизнес-смысл, а не тип. |

## 6. Проектирование REST API

| Термин | Определение | В OAS |
|---|---|---|
| REST | Архитектурный стиль: ресурсы, адресуемые URL, и стандартные HTTP-методы. | Основа структуры `paths`. |
| Ресурс | Бизнес-сущность, доступная по URL. | Существительное во множественном числе: `/wallets`. |
| Коллекция / элемент | `/wallets` — коллекция, `/wallets/{walletId}` — элемент. | — |
| Endpoint | Конкретная точка API: метод + путь. | = Operation. |
| GET | Чтение. Безопасный и идемпотентный. | Без `requestBody`. |
| POST | Создание ресурса или запуск действия. Не идемпотентен по умолчанию. | См. «Идемпотентность». |
| PUT | Полная замена ресурса. Идемпотентен. | — |
| PATCH | Частичное изменение. | — |
| DELETE | Удаление. Идемпотентен. | — |
| Действие (action) | Операция, не сводимая к CRUD: подтвердить, отменить. | `POST /wallet-applications/{id}/confirm` |
| Идемпотентность | Повтор запроса даёт тот же результат без повторного эффекта. | Заголовок `Idempotency-Key` — [[oas-conventions#7. Заголовки]]. |
| HTTP status codes | Коды результата. | Минимальный набор см. ниже. |
| 200 OK | Успех с телом. | — |
| 201 Created | Ресурс создан. | Заголовок `Location`. |
| 202 Accepted | Запрос принят, обработка асинхронная. | Вернуть id и статус для опроса. |
| 204 No Content | Успех без тела. | — |
| 400 Bad Request | Некорректный запрос (синтаксис, валидация). | — |
| 401 Unauthorized | Нет или недействительна аутентификация. | — |
| 403 Forbidden | Аутентифицирован, но нет прав. | — |
| 404 Not Found | Ресурс не найден. | — |
| 409 Conflict | Конфликт состояния (например, кошелёк уже есть). | Бизнес-код ошибки. |
| 422 Unprocessable Content | Запрос корректен, но нарушает бизнес-правило. | Бизнес-код ошибки. |
| 429 Too Many Requests | Превышен лимит запросов. | Заголовок `Retry-After`. |
| 500 Internal Server Error | Внутренняя ошибка. | — |
| 502 / 503 / 504 | Ошибка, недоступность или таймаут зависимой (внешней) системы. | Описывать, если зависим от платформы ЦР, АБС. |
| Problem Details | Стандарт формата ошибок, RFC 9457 (заменил RFC 7807): `type`, `title`, `status`, `detail`, `instance` + свои поля. | Принятый формат — [[oas-conventions#8. Ответы и ошибки]]. |
| Бизнес-код ошибки | Машиночитаемый код конкретной ситуации: `WALLET_ALREADY_EXISTS`. | `enum` кодов + таблица в `description`. |
| Пагинация | Разбиение списка на страницы: offset/limit или cursor. | Параметры `limit`, `cursor`; в ответе `nextCursor`. |
| Фильтрация / сортировка | Параметры выборки. | `dateFrom`, `dateTo`, `sort=-createdAt`. |
| Версионирование API | Управление несовместимыми изменениями. | В пути `/v1` или в заголовке. |
| Обратная совместимость | Изменение не ломает существующих клиентов (добавление необязательного поля). | Удаление или переименование полей — breaking change. |
| ETag / If-Match | Версия ресурса для оптимистичной блокировки. | 412 при несовпадении. |
| Correlation ID / Request ID | Сквозной идентификатор запроса для трассировки по системам. | Заголовок `X-Request-Id`. |
| Long-running operation | Операция, которая долго выполняется. Шаблон: 202 + ресурс статуса + опрос или callback. | Ресурс `.../{id}` со статусом. |
| Деньги в API | Сумма — целое в минимальных единицах (копейках) или десятичная строка; валюта — код ISO 4217. | Принятый способ — [[oas-conventions#6. Типы данных]]. |
| Дата и время | ISO 8601 / RFC 3339 с часовым поясом. | [[oas-conventions#6. Типы данных]] |
| Номер телефона | Формат E.164. | [[oas-conventions#6. Типы данных]] |
| UUID | Универсальный уникальный идентификатор. | `format: uuid` для id ресурсов. |
| Naming conventions | Соглашения об именах: пути — kebab-case, поля — camelCase, enum — UPPER_SNAKE_CASE. | Принятые правила — [[oas-conventions]]. |

| ETL | Extract, Transform, Load — выгрузка, преобразование, загрузка данных. | — |

| Термин | Определение | В OAS |
|---|---|---|
| Timeout | Максимальное время ожидания ответа. | НФТ в `description`; 504 при превышении. |

| Circuit breaker | Временное отключение вызовов к сбоящей системе. | 503 при открытом выключателе. |

| Outbox | Паттерн: событие записывается в БД вместе с изменением, затем отправляется. | — |
| Saga | Распределённая транзакция как цепочка шагов с компенсацией. | Промежуточные статусы. |
| Компенсация | Действие, отменяющее эффект шага (возврат средств при сбое зачисления). | Статусы вида `REFUNDED`, `FAILED`. |
| Rate limiting | Ограничение частоты запросов. | 429 + `Retry-After`. |
| SLA / SLO | Соглашение / цель по уровню сервиса (доступность, время ответа). | НФТ. |
| Latency / Throughput | Задержка / пропускная способность. | НФТ. |

| Термин | Определение | В OAS |
|---|---|---|

| Статусная модель (state machine) | Состояния сущности и допустимые переходы. | `enum` статуса + описание переходов. |
| Модель данных / ER-диаграмма | Сущности, атрибуты и связи. | `components.schemas`. |
| Логическая модель | Модель данных без привязки к технологии. | Основа схем. |
| Sequence diagram | Диаграмма последовательности вызовов между системами (UML, PlantUML, Mermaid). | Порядок операций и интеграций. |
| PlantUML | Текстовый язык описания UML-диаграмм (`@startuml … @enduml`); проверяется и рендерится `plantuml.jar`. | Второй артефакт skill — sequence-диаграмма `<имя>-sequence.puml`. |

| Open questions | Список нерешённых вопросов. | Фиксировать отдельно, не додумывать в OAS. |
| Допущение (assumption) | Принятое без подтверждения решение. | Явно помечать в `description`. |

## 10. Сквозное соответствие: требование → элемент OAS

| Что есть в задаче или контексте | Во что превращается в OAS |
|---|---|
| Epic / продукт | `info`, один файл OAS или группа `tags` |
| Фича / Story | `tag` + набор операций |
| Шаг сценария с обращением к бэкенду | Operation (`path` + метод + `operationId`) |
| Шаг только в интерфейсе | Нет операции (отметить в описании сценария) |
| Бизнес-сущность (кошелёк, заявка, договор) | `components.schemas.*` и ресурс в `paths` |
| Атрибут сущности | `properties` с `type`, `format`, `pattern`, `required` |
| Статус сущности | `enum` + описание переходов |
| Предусловие или бизнес-правило | Валидация + ответ 403/409/422 с бизнес-кодом |
| Альтернативный или исключительный сценарий | Ответ с кодом и примером в `responses` |
| Недоступность внешней системы | 502/503/504 + `Retry-After` |
| Асинхронный шаг (ответ платформы позже) | 202 + ресурс статуса и/или `callbacks` / `webhooks` |
| Повторное нажатие, денежная операция | `Idempotency-Key` |
| Роль пользователя | `security`, `scopes`, отдельные `tags` для бэк-офиса |
| НФТ (время ответа, лимиты) | `description`, `x-*`, ответ 429 |
| ПДн | `x-sensitivity`, маскирование, `writeOnly` ([[sensitive-data]]) |
| Ключ задачи Jira | `x-jira-key` на операции |
| Неясность в требованиях | Open question, не выдумывать поле |
